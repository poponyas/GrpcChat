# Roadmap GrpcChat

Цель: удобный терминальный мессенджер, в котором можно вести несколько групп и личных диалогов, быстро между ними переключаться и не терять историю.

## Этап 0 — рабочая основа · готово

- [x] Сервер и CLI запускаются отдельно.
- [x] Регистрация, вход, сохранённая сессия и выход с её отзывом.
- [x] Группы: создание, приглашение, список участников, удаление и выход.
- [x] Личные диалоги: одна переписка для пары пользователей.
- [x] Переключение между чатами по номеру, имени или ID.
- [x] Отправка с подтверждением сохранения и получение сообщений онлайн.
- [x] История PostgreSQL с курсорной пагинацией.
- [x] Несколько терминалов, уведомления и переподключение.
- [x] Проверка прав доступа, TLS для внешнего адреса, завершение сервера.
- [x] Unit- и интеграционные тесты с race detector, конфигурация CI.
- [x] Инструкция запуска и описание архитектуры.

Критерий: два пользователя создают группу, обмениваются сообщениями, переходят в личный диалог, возвращаются в группу и читают историю после нового входа. Посторонний пользователь не может прочитать или изменить переписку. Сквозные тесты проверяют эти основные сценарии; запуск клиентов описан в README.

## Этап 1 — ежедневное удобство · следующий

Полноэкранный TUI: слева список чатов, справа история, внизу поле ввода. Переключение стрелками/Tab, поиск по чатам, многострочный ввод, прокрутка истории и сохранение введённого текста при переключении. Входящие сообщения не должны мешать набираемому тексту.

Сначала отделить представление от существующих команд клиента, затем добавить TUI поверх того же API. Сохранить построчный режим для скриптов и простых терминалов.

Критерий: можно общаться в пяти чатах, менять активный чат с клавиатуры, листать историю и получать входящие, сохраняя набираемый текст.

## Этап 2 — непрочитанные и надёжное восстановление

Хранить позицию прочтения для пары пользователь–чат. Возвращать в списке чатов последнее сообщение и число непрочитанных. Добавить синхронизацию пропущенных событий после переподключения и ключ идемпотентности отправки, чтобы безопасно повторять запрос при сетевой ошибке. Для гарантированного выхода события после записи использовать transactional outbox.

Зависимость: сначала согласовать стабильный порядок сообщений и протокол синхронизации; затем менять UI-счётчики.

Критерий: после отключения сети и перезапуска клиента непрочитанные восстанавливаются, повторная отправка одного запроса не дублирует сообщение, все пропущенные сообщения доступны без ручного поиска страниц.

## Этап 3 — управление сообществами

Переименование группы, передача владельца, назначение администраторов, приглашения по ссылке с ограниченным сроком и отзывом. Явный выбор доступа приглашённого пользователя к прежней истории. При необходимости — публичные группы и самостоятельное вступление как отдельный режим.

Критерий: владелец может передать группу и выйти; роли проверяются на сервере; отозванная ссылка не работает; личный диалог всегда сохраняет двух участников.

## Этап 4 — учётные записи и эксплуатация

Смена и восстановление пароля, список устройств/сессий, отзыв всех сессий, ограничение частоты регистрации и входа. Уборка истёкших сессий, резервное копирование с проверкой восстановления, health/readiness, метрики и журнал ошибок стримов. Упаковка сервера в контейнер, сборки CLI для Linux/macOS/Windows и проверяемый процесс релизов.

Этот этап нужен перед открытой регистрацией и постоянным размещением сервера в интернете.

Критерий: пользователь восстанавливает доступ и завершает чужую сессию; оператор восстанавливает базу из резервной копии и диагностирует сбой по метрикам; клиент устанавливается готовым бинарником.

## Этап 5 — расширения по потребности

Поиск сообщений и пользователей на сервере вместо загрузки всего каталога; редактирование/удаление сообщений с правилами доступа; ответы и упоминания; вложения через объектное хранилище. Для нескольких серверов — внешний брокер событий и подписки между экземплярами. Сквозное шифрование требует отдельного проектирования ключей, устройств и восстановления.

Каждую возможность добавлять после подтверждения её необходимости в реальном использовании.

## Порядок работы

Ближайший законченный результат — этап 1, затем этап 2. Этап 4 выполнять до публичного запуска; этап 3 можно двигать параллельно продуктовым потребностям. Календарные сроки зависят от выбранного интерфейса и условий размещения, поэтому этапы привязаны к проверяемому поведению.
